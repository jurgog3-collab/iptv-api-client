# IPTV API

Короткий опис того, як налаштована авторизація на API, і що саме можна з нього
отримати. Цей док покликаний швидко ввести в курс справи того, хто буде писати
клієнта для дочірнього сервісу — без зайвих деталей по внутрішній кухні.

Якщо коротко: до API ходимо за схемою `https://host/api/v1/<що взяти>/<токен>/<час>`,
де токен рахується щоразу новий і живе максимум хвилину.

---

## Як працює токен

За основу взято «ковзне» часове вікно. Обидві сторони (сервер і клієнт) знають
один спільний секрет `S`. Клієнт на кожен запит рахує токен від поточної хвилини:

```
часова хвилина (slot) = unix-час // 60
токен                 = sha256( S + slot )
```

Тобто токен — це просто хеш від конкатенації секрету й номера хвилини. Раз на
хвилину він змінюється сам собою, тож один і той самий токен неможливо
перехопити й застосувати пізніше — через 60 секунд він вже не зайде.

Щоб сервер зрозумів, на яку саме хвилину рахував клієнт, разом із токеном
передається і сам час запиту `ts` (unix-секунди). Підсумкова адреса виглядає так:

```
GET /api/v1/status/<токен>/<ts>
```

На сервері перевірка досить проста:

1. різниця між поточним часом сервера і `ts` не більша за 120 секунд —
   інакше це або застарілий запит, або «з майбутнього»;
2. для `ts` рахується очікуваний токен по формулі вище, і порівнюється з тим,
   що прийшло. Береться не лише поточна хвилина, а й сусідні (мінус і плюс один
   слот) — щоб клієнт, який рахував токен рівно на межі хвилини, не відвалився.

Оскільки секрет ніколи не передається в запиті (передається лише його хеш),
перехопити сам ключ неможливо.

### Приклад клієнта на Python

```python
import hashlib
import time
import urllib.request
import json

API_BASE = "https://iptv.osnova.tv/api/v1"
SECRET   = "секрет_клієнта"        # спільний секрет з сервером

def token_for(ts: int) -> str:
    slot = ts // 60
    return hashlib.sha256(f"{SECRET}{slot}".encode()).hexdigest()

def api_get(path: str):
    ts = int(time.time())
    token = token_for(ts)
    url = f"{API_BASE}/{path}/{token}/{ts}"
    with urllib.request.urlopen(url) as r:
        return json.loads(r.read())

# приклад: список пакетів
data = api_get("packets")
print(data)
```

`path` підставляється вже без `{token}` і `{ts}` — вони дописуються автоматично.
Приклад: `api_get("user/aid/10002")` дасть запит на
`/api/v1/user/aid/10002/<токен>/<ts>`.

> Секрет тримається тільки на сервері й у клієнті. Не кладіть його в публічний код.

---

## Динаміка токена — для чого це все

Головна ідея схеми — зробити так, щоб **ключ змінювався на кожен запит**.
Статичний ключ, який був раніше, небезпечний тим, що його достатньо вкрасти один
раз — і доступ отримано назавжди. Тут же перехоплений токен перестає працювати
через кілька десятків секунд, і для наступного запиту потрібен новий.

Тому клієнт завжди будує адресу зі свіжим токеном, а не зберігає готовий.

---

## Ендпоінти

Усі відповіді — JSON (`application/json; charset=utf-8`). Параметри `{token}` і
`{ts}` — це все ті самі динамічні токен і час запиту.

### Сервіс і довідкові дані

| Метод | Опис |
|---|---|
| `GET /api/v1/status/{token}/{ts}` | перевірка, що API живий |
| `GET /api/v1/channels/{token}/{ts}` | каталог каналів |
| `GET /api/v1/packets/{token}/{ts}` | список пакетів каналів (+ чи пакет у вільному доступі) |
| `GET /api/v1/services/{token}/{ts}` | список сервісів (тарифів) з кількістю абонентів |

### Загальні зрізи

| Метод | Опис |
|---|---|
| `GET /api/v1/users/{token}/{ts}` | абоненти, що мають (або мали) сервіс чи пакет, з їхніми каналами |
| `GET /api/v1/user/{token}/{ts}` | поточний зріз без прив'язки до конкретного aid (лише з сервісом) |
| `GET /api/v1/user/{token}/{ts}/{aid}` | інфо одного абонента за `aid` |

`/users` віддає лише абонентів, які мають (або мали) хоча б один сервіс чи пакет —
тобто тих, хто є у `services_user`. Користувачі без жодного сервісу до вибірки не
потрапляють, щоб список не розростався зайво. Для одного абонента зручніші точкові
пошуки (див. розділ пошуку клієнта нижче).

### Службові зв'язки

| Метод | Опис |
|---|---|
| `GET /api/v1/packets/{packetid}/users/{token}/{ts}` | абоненти, що мають пакет |
| `GET /api/v1/packets/{packetid}/channels/{token}/{ts}` | канали у пакеті |
| `GET /api/v1/channels/{channelid}/users/{token}/{ts}` | клієнти з доступом до каналу |
| `GET /api/v1/services/{sid}/packets/{token}/{ts}` | пакети сервісу |
| `GET /api/v1/services/{sid}/users/{token}/{ts}` | абоненти сервісу |

### Комбіновані

| Метод | Опис |
|---|---|
| `GET /api/v1/packets/{packetid}/{token}/{ts}` | пакет + його канали + абоненти |
| `GET /api/v1/channels/{channelid}/{token}/{ts}` | канал + його пакети + клієнти |

### Перевірка оновлень і значення з config

У системі є таблиця `config`, де кожен параметр зберігає значення і час своєї
останньої зміни. Якщо дочірньому сервісу треба знати, коли щось оновилось (скажімо,
вирішити, чи перечитувати список абонентів), є кілька зручних ендпоінтів.

Підтримувані ключі:

`user_list`, `services_user`, `services`, `free_list`, `black_list`, `channels`,
`chan_packs`, `serv_packets`, `packets`, `custom_ip_packs`, `custom_aid_packs`.

| Метод | Опис |
|---|---|
| `GET /api/v1/config/{token}/{ts}` | усі ці параметри зі значенням, хешем і часом оновлення |
| `GET /api/v1/config/{group}/{token}/{ts}` | вибірка за групою (див. нижче) |
| `GET /api/v1/updates/{token}/{ts}` | лише час останніх оновлень усіх параметрів |
| `GET /api/v1/updates/{group}/{token}/{ts}` | час оновлень лише для групи чи ключа |

У якості `{group}` можна вказати:

- `core` — три головні зрізи разом: `user_list`, `services_user`, `services`;
- `all` — всі дозволені ключі;
- або конкретний ключ, наприклад `user_list`, `services`, `black_list`.

Тобто трійку `user_list` + `services_user` + `services` можна взяти одним запитом
(`core`), або по одному (`user_list`, `services_user`, `services`).

Приклад відповіді для `updates/core`:

```json
{
  "ok": true,
  "server_time": 1793718601,
  "updated_ts": {
    "user_list": 1793727901,
    "services_user": 1793718601,
    "services": 1793715001
  }
}
```

`updated_ts` — unix-час останньої зміни кожного ключа (або `null`, якщо ключ ще не
заданий). Порівнюючи `server_time` з `updated_ts`, клієнт вирішує, чи дані застаріли.

`config` версія віддає те саме, але розширено — значення і хеш:

```json
{
  "ok": true,
  "group": "core",
  "found": 3,
  "server_time": 1793718601,
  "config": {
    "user_list": { "param": "user_list", "value": "1793727901",
                   "value_hash": "...", "date": "2026-11-01 12:00:00",
                   "ts": 1793727901, "is_set": true }
  },
  "updated_ts": { "user_list": 1793727901 }
}
```

### Пошук клієнта

Загальний запит повертає все, що знайдено по клієнту: сервіси, пакети й канали.
Через `{field}` можна залишити лише одну секцію — `services`, `channels` або
`packets`.

| Метод | Опис |
|---|---|
| `GET /api/v1/user/ip/{ip}/{token}/{ts}` | клієнт(и) по IP (шукає по `ip` або `ips`) |
| `GET /api/v1/user/ip/{ip}/{field}/{token}/{ts}` | те саме, але лише секція `field` |
| `GET /api/v1/user/ls/{ls}/{token}/{ts}` | клієнт(и) по особовому рахунку |
| `GET /api/v1/user/ls/{ls}/{field}/{token}/{ts}` | те саме, лише секція `field` |
| `GET /api/v1/user/aid/{aid}/{token}/{ts}` | клієнт(и) по aid |
| `GET /api/v1/user/aid/{aid}/{field}/{token}/{ts}` | те саме, лише секція `field` |

## Помилки

| Код | Тіло | Коли |
|---|---|---|
| 401 | `{"ok": false, "error": "unauthorized"}` | невірний або застарілий токен |
| 400 | `{"ok": false, "error": "invalid_ip"}` та ін. | некоректний параметр запиту |
| 404 | `{"ok": false, "error": "packet_not_found"}` | об'єкт не знайдено |
| 500 | `{"ok": false, "error": "no_snapshot"}` | немає актуальних даних у системі |

Найчастіша причина 401 — клієнт рахує токен на сервері, а час на пристрої
розсинхронізований. Якщо різниця в часі більша за дві хвилини, токен не прийметься,
тож годинник має бути синхронізований (NTP).
